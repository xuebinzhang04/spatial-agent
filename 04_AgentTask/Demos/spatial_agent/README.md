# SpatialAgent research demo

From the SpatialAgent directory, start or restart the page with:

```bash
python -u 04_AgentTask/Demos/spatial_agent/run.py
```

The page uses fixed port **8768**. If this project's server is already listening there, the launcher stops that process and starts the new one on the same port. It will not stop an unrelated service or switch ports. Refresh the browser after restart. In VS Code Remote SSH, open the forwarded port 8768.

## Research sections and selectors

The page is a concise research presentation with three parts. **Overview** states the research framing: spatial memory under passive viewing and interactive exploration, plus the local-state / global-memory (build, update, freeze) split. **Tasks & Example Cases** has one card per task. **Step Through a Case** is the frame-by-frame replay explorer. The generation audit, Online Demo and Research Notes are collapsed under **Appendix**.

Each task card is generated by `build.py` from one recorded episode listed under `showcase` in `demo.json`. A card contains:
- the case GIF;
- the task question and its design (the information gap that interaction must close, from `examples.json`);
- a phase timeline with step ranges and the task actions, derived from the episode frames;
- "this case" facts, which are the episode's global-memory variables extracted by `scripts/experiments/task_generation_audit.py` and filled into the `facts` templates of `examples.json`;
- the success test;
- a link that opens the same episode in the explorer (`static/cases.js`).

The shape identification card also shows a before/after evidence comparison: public frame 0 beside the public frame reached by the recorded camera actions that precede `SUBMIT_SHAPE`, with the run-length camera path. `build.py` derives both frames and the path from the trajectory. At build time it reads the generator's revealing camera path (`ambiguity_witness.actions` in the step-0 state of `privileged.jsonl`) and fails unless every recorded action before `SUBMIT_SHAPE` equals it exactly, in order; the caption then says the path matches the one the generator found when it checked that the target and one initial twin differ in at least 10% of foreground pixels. Only that pass/fail result is used; the witness itself and its pixel statistics are not written to the page or catalog. The comparison is labelled a privileged oracle reference, not a VLM result.

Showcase cases are chosen to pass the generation audit and are recorded with the current generator by `scripts/experiments/record_showcase_cases.py`. Two sources are used:
- the Shape3D cards come from `05_Experiment/results/showcase-cases-20261111`: an initial-pixel-ambiguity shape case and an exact-depth pose case, recorded on CPU;
- four AI2-THOR cards come from `05_Experiment/results/showcase-cases-native-449135` (`record_showcase_native.slurm`, one MIG slice, 512 px).

Missing and moved object still use the 512 px state-verified re-renders of the 2026-10-19 action tours (L1 protocol, target visible at start).

The recorded demo follows one flow: select simulator/task/model/case, inspect the model input/output, play the scene, and read the compact state beside it. Single-camera cases have no camera selector. Multi-camera snapshots use one selector. Full DeliveryBench videos remain the default, with synchronized camera maps in one disclosure.

The sidebar contains objective, current action, policy, phase, remaining actions, reward and a short resource summary. Difficulty is collapsed. Task definitions, actions, verification, simulator variables and limitations share one disclosure below the display; provenance and the current raw transition share another. Delivery map tools remain in their own disclosure outside the sidebar. Empty model-output and feedback blocks are hidden. The old focus/comparison/export controls and the standalone mechanism inspector were removed.

Online Demo retains its simulator/model connection and action controls. Its inference response follows those controls. Online results use the same scene player. Selecting an offline recording never executes a simulator or model.

The active catalog has 24 recordings: 20 native/geometry episodes, one historical manual delivery cutoff and three fixed courier runs. Two successful Qwen runs cover the same admitted courier case. Selecting SimWorld defaults to the Qwen full-process recording: 233 observation samples over approximately 249 seconds, with seven high-level decisions. Decision snapshots remain an explicit alternate mode. The retired graph prototype and mechanism inspector sources are preserved under `archive/agent-interaction/legacy-demos/`.

## Native visual observation protocol

New native sessions return RGB without object-number overlays. `view_step` identifies the observed image; use `view:STEP:X:Y` in `object_id` or submitted location fields, with normalized top-left image coordinates in `[0,1)`. Private instance masks resolve the visible pixel to an evaluator identity, including past memorization views. Future frames, background pixels and ambiguous overlapping masks are rejected. Native manipulation still requires current visibility and reach. Internal Oracle actions retain private-ID compatibility; the public demo API rejects numbered object references. Goal instructions use object types; duplicate same-type goal descriptions are rejected rather than guessed. This may invalidate previously accepted generated native cases and requires a fresh allocated validation run. Shape candidate labels and placement-slot markers are separate task controls, not object IDs.

Historical images, videos and outcomes retain their actual numbered observations and are labelled as the previous protocol. They do not establish performance under unnumbered observations. Lightweight/contract tests use synthetic native events; no new Unity rollout has been run.

## Online environment and inference

Use the existing spatialagent environment for lightweight simulation:

```bash
module load conda
conda activate spatialagent
python 04_AgentTask/Demos/spatial_agent/run.py --environment shape3d --task shape_identification
```

The normal page server can create these tasks from Online Demo without a startup task. For native AI2-THOR, use its registered Python runtime in a scheduler allocation and `--environment native --task <task> --scene FloorPlan1`. The server's interpreter must contain that simulator's dependencies.

To call an already running inference service, add `--model-url http://127.0.0.1:8000/v1 --model <actual-served-model-id>`. Optional credentials are read server-side from `SPATIAL_MODEL_API_KEY`. The page lists Manual API and local checkpoints from `01_Models`, including `Qwen3.8-27B`, even before a service is connected. Select a model, enter its service base URL, and click **Connect selected model** to verify `/models` identity. Checkpoint availability, endpoint configuration and verified service status are displayed separately. The demo does not load model weights or start a second model server. Model identity, returned action, execution and errors are logged. Only public observations, raster views, allowed actions and the policy's own action history enter inference; evaluator results and privileged witnesses are excluded.

Delivery requires the dedicated UE executable running in a Slurm allocation and a Qt main-thread loop. The existing `scripts/experiments/launch_interaction_demo.py --map small-city-11` and `simworld_interaction_demo.slurm` now use this shared `run.py` on port 8767. They retain runtime isolation, logs, scripted tour and stop/cleanup. Optional `DEMO_MODEL_URL` and `DEMO_MODEL` configure an existing model service for that launch. Recheck account/budget/queue before submitting a paid job. A live city/reset change requires restarting the allocation; use Read environment state to attach the page to that session.

| API | Behavior |
| --- | --- |
| `GET /api/capabilities` | Local model inventory, configured/verified service, observation-only mode and active simulator/task |
| `POST /api/model` | Connect the selected model to a service after verifying its served ID |
| `GET /api/state` | Current public views/state; does not take an action |
| `POST /api/reset` | Generate and reset an implemented lightweight/native adapter |
| `POST /api/action` | Execute one action; reject a mismatched expected simulator/task |
| `POST /api/infer` | Propose an action, or execute it when `execute=true` |
| `POST /api/stop` | Stop the shared session, including during a long operation |

The server is loopback-only and operations are serialized. Repeated state reads update the current frame rather than duplicate action counts or reward. Session logs and manifests go to a new `05_Experiment/results/demo-session-<timestamp>/`, or the supplied `--run-dir`.

## Replace historical object-number overlays

The current native renderer no longer draws object-number overlays, but historical source PNGs and MP4s have the numbers baked in. They cannot become raw observations through masking or invented pixels. The homepage now uses state-verified unnumbered re-renderings for the six native task families; historical numbered source observations remain archived. The two procedural Shape3D examples do not have object-number overlays.

`rerender.py` replays each original native action sequence in the registered simulator. It checks the object set, identity binding, positions, rotations, object states, camera pose, task progress/history, phases and rewards against the original private evidence. It saves a separate set of unnumbered frames and clips, preserving the historical recordings. This is rendering-only replay, not a new policy rollout on unnumbered observations. A rendering-only observation callback avoids redefining historical task goals using the current public reference protocol.

On a normal cluster terminal, check current account/budget and queue availability before submitting:

```bash
hyakusage -a video
sinfo -s
squeue --me
sbatch scripts/experiments/rerender_demo.slurm
```

The prepared job uses the registered native Python, software Vulkan and an allocated runtime. It publishes `presentation/clean-frames.json` only after all native cases pass, then rebuilds the site. The builder checks source trajectory and frame/video hashes, replaces default display images/GIFs/videos, and retains original observation images and provenance. Native clean-media rendering completed in job 388731. The displayed presentation episodes were subsequently refreshed at 512×512 capture resolution in job 389765 with state/reward/phase checks; other historical clean media remain preserved. Current Codex scheduler access has been verified. A failed or mismatched replay retains its diagnostics and does not publish a new clean-media manifest.

## Independent inference and online observation

The inference worker owns the environment and model calls. The presentation server can separately read the worker's public event stream, so viewing does not require importing a simulator or starting another model instance.

Start the existing model service with `bash scripts/serve_qwen.sh` in an allocated GPU runtime. Then run the worker from the SpatialAgent root, using the `spatialagent` conda environment for Shape3D:

```bash
python 04_AgentTask/Demos/spatial_agent/rollout.py \
  --environment shape3d --task shape_identification \
  --model Qwen3.8-27B --model-url http://127.0.0.1:8000/v1 \
  --run-dir 05_Experiment/results/qwen-shape-online
```

Use a fresh run directory on each launch. On any host with access to that shared directory, independently start the observation server:

```bash
python 04_AgentTask/Demos/spatial_agent/run.py \
  --observe-run 05_Experiment/results/qwen-shape-online
```

The run must first contain its worker manifest. The page follows its public observations, model input summaries, actual model outputs, actions and transitions every two seconds. Its timeline imports complete public events, including steps produced between polls. Model input summaries identify the input environment step and image streams; the scene player shows the recorded visual context. Observation mode rejects reset/action/inference/model-connection requests. **Stop viewer** only stops the presentation server, leaving the independent worker running. Completed runs can be viewed through the same entrypoint. The headless worker currently supports Shape3D and native AI2-THOR tasks; Delivery retains its allocated Qt runtime entrypoint.

For interactive testing instead, run `run.py` without `--observe-run`, choose the downloaded model and connect its endpoint. Choosing a checkpoint never silently loads GPU weights. Qwen requests disable thinking for the existing one-action JSON protocol. Worker snapshots and metadata are published atomically, and the observation process does not modify worker evidence.

## Interaction-first case regeneration

The [expectation registry](../../CustomAgentTasks/expectations.json) defines the eight tasks' required abilities, settings, shortcut controls and review risks. New missing/moved cases use `active_scan_v1`: hidden initial target, explicit memory commitment, stage clocks, a frozen notebook and strict pre-change evidence checks. Memory-maze regeneration uses `explicit_recall_v1`. New shape cases require an actual initial pixel ambiguity pair and a verified revealing camera translation; shared orthographic silhouettes alone do not qualify. Historical recordings are unchanged and do not establish the revised protocols' native/model behavior.

`rollout.py` writes `interaction-analysis.json` after every inference using `scripts/experiments/analyze_interaction.py`; the observer stays read-only. The same analyzer can inspect historical trajectories and private pose evidence. Repetition is a diagnostic flag, not an automatic assertion of ineffective behavior.

`scripts/experiments/regenerate_task_cases.py prepare --output <fresh-results-path>` freezes three recipes per task. Its `run` command requires a scheduler allocation and a configured model service, executes the exact frozen settings, saves uncorrected model trajectories with raw RGB and separate evaluator state, and retains failed setting checks. `regenerate_task_cases.slurm` provides an allocated execution entrypoint; account and resource availability must be checked before submission. Recipes and recorded attempts are not automatically approved examples. Full survey feasibility, relevant shortcut controls, observation-limited replay and expectation review must precede demo replacement. Current numbered historical media must not be described as new unnumbered examples.

High-resolution native media uses state-verified rendering-only replay. `--presentation-only` refreshes the selected research examples while retaining existing clean media for other historical episodes. `--render-size 512` changes resolution only for capture, verifies state, and restores the original policy resolution before the next recorded action. This does not establish model performance on higher-resolution inputs.

## Full courier process versus model decisions

A native `MOVE` call covers an extended trip. Seven model decisions therefore do not mean seven simulator frames. The process-equipped Qwen recording (`389912`) includes 233 actual in-action observations, timestamped public state and three 248.76-second videos. In the fixed courier task, the process-equipped episode is selected first. **Full process** synchronizes first-person, global/local map videos and public state; **Decision snapshots** retains exact prompt/response inspection at the API boundaries. The measured capture cadence is displayed rather than assuming the target timer rate. Videos contain no interpolated scene frames.

The DeliveryBench subsection in Environment & task demos contains the ten-city interactive map, POIs, approximate routes and resource estimates. It has no separate sidebar entry. Recorded courier position/state can be followed; uncheck **Follow recorded courier** to inspect the diagram independently. Diagram controls do not execute simulator actions. **Online inference response** exists only in the independent Online Demo section.
