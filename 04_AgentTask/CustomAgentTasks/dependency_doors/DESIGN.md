# 真实容器访问依赖与有序检索

原型训练的是“先满足前提，后执行目标动作”。标准 iTHOR 没有通用钥匙锁系统，因此迁移版采用真正的关闭容器：柜门/抽屉/冰箱的可见性与碰撞决定能否取物，不添加虚构钥匙状态。

## 任务构造

当前生成器优先选择场景里已经位于关闭容器中的小物体。自然内容不足时，通过原生拿取/容器放置布置额外物体，并保存完整的实际对象姿态；这些布置动作只发生在任务生成阶段。公开编号在布置完成后绑定，避免原生模拟器重建内部 ID 后出现指令错配。每个来源必须有实际成功的原生开门、关门、拿取和台面放置见证，还会检查同一取物动作在容器关闭时被原生模拟器拒绝。只检查可见性不足以证明可操作，因此会搜索并实际测试附近的交互视角。只有全部通过的绑定才成为任务；没有足够原生可执行检索订单的配置明确拒绝，不用符号状态补足。相同环境实例和种子重置时复用已验证的任务绑定，并原生重置场景。

代理按顺序完成 OpenObject → PickupObject → 导航 → PutObject，并关闭使用过的源容器，最后 FINISH。动作使用可见对象编号；没有目标坐标或可达图。持物容量是模拟器真实的一只手，放置结果从真实 parentReceptacles 与 inventoryObjects 验证。

L1 一个检索订单，L2 两个订单，L3 三个订单。订单可共用源容器，生成器不假设每个布局都有三个可操作的容器；每次配送仍须真实拿取、运输、放置并关好源容器。每个对象必须在规定顺序中被真实拿取并放置；提前搬走后续对象不会直接完成该阶段。所有物体最终仍须在目标台面、手为空、源容器关闭。提前提交失败。

## 有价值的训练模式

- 短序列课程：先学习可见性和开合前提，再组合单手持物、导航与放置。
- 干预对照：相同任务的容器预先打开/关闭，检验策略是否理解访问条件。
- 顺序组合：增加容器数、改变对象和容器绑定，观察错误拿取、遗漏关闭和阶段混淆。
- 布局迁移：开发/验证/测试使用不同 FloorPlan，避免仅记固定门牌位置。

成功奖励只在全部物理条件成立时为 1，减去有界行动成本；没有“对象找对但位置错误仍得满分”的奖励。指标包括完整成功、配送数、源容器关闭状态、行动数与无效动作。

限制：多容器任务是访问与持物依赖链，不是需要钥匙解锁房门的环境；这些容器之间没有虚构的锁链。课程难度是结构定义，未由 VLM 成功率校准。

生成调试记录中的 generated_container_placements 使用布置前的原生对象 ID，表示历史布置输入；评分使用 orders 中的布置后原生 ID 和当前真实状态。代理只使用 episode 内稳定的 object_NNN 编号。
